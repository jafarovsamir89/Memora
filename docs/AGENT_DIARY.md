### 2026-11-01 — ACT-0069: corrupted key-envelope fail-closed

Расширен isolated storage probe: он создаёт synthetic SQLCipher DB + Android Keystore wrapping key, сохраняет encrypted test row, портит последний byte только отдельного encrypted envelope, проверяет `DatabaseKeyUnavailableException`, идентичность DB bytes и повреждённого envelope до/после отказа; затем восстанавливает fixture envelope из in-memory backup, перечитывает ту же запись, очищает все byte arrays и удаляет только named synthetic DB/envelope/key.

Redmi Android13 и API26 emulator прошли `corrupt_envelope_refused_without_database_loss=true`; остальные storage cases также прошли: wrong/missing key, missing envelope, damaged DB, correct-key reopen, plaintext check, WAL disabled. `:app:assembleDebugAndroidTest :app:lintDebug --no-daemon` — BUILD SUCCESSFUL. Это тест целостности envelope, не механизм rotation или резервного восстановления пользовательского архива. P1 остаётся открытым по key rotation/recovery/uninstall/restore, hard crash/power loss/disk faults, license/signing gates.

Git на момент записи: локальные незакоммиченные изменения; после проверки diff и секретов синхронизировать package и подтвердить remote.

### 2026-11-01 — ACT-0068: corrupted SQLCipher database fail-closed

Расширен synthetic storage probe: создаётся отдельная SQLCipher DB с контрольной synthetic записью, после close в encrypted bytes меняется один байт, попытка открыть/прочитать должна завершиться отказом и не менять tampered file. Затем probe восстанавливает исходный encrypted fixture в памяти, проверяет сохранённую запись, очищает массивы bytes и удаляет только synthetic DB, envelope и Keystore alias.

На физическом Redmi Android13 и API26 emulator storage probe прошёл с `database_corruption_refused_without_overwrite=true`, вместе с missing key/envelope, wrong key, disabled WAL, DB plaintext checks. `:app:assembleDebugAndroidTest :app:lintDebug --no-daemon` — BUILD SUCCESSFUL. Никакие user/legacy stores не открывались. Этот probe не является disk-full/power-loss/hardware crash тестом; P1 остаётся открытым.

Код и обновлённые статусы ещё не переданы в Git на момент записи; следующий шаг — проверить secret-pattern scan/diff, синхронизировать package и затем продолжать оставшиеся P1 gates.

### 2026-11-01 — ACT-0067: synthetic process-death recovery на API 26 и Redmi

После ACT-0066 добавлен отдельный opt-in instrumentation probe для реального force-stop во время открытой synthetic SQLite транзакции. Probe создаёт только тестовую БД и Keystore alias, пишет один committed row, затем начинает транзакцию со второй незавершённой строкой и выводит только статический readiness marker. Host останавливает процесс Memora; следующий instrumentation process открывает ту же защищённую БД, проверяет наличие committed row, отсутствие uncommitted row и отсутствие обоих plaintext markers, затем удаляет только synthetic DB/envelope/test alias.

Результат: API26 emulator и физический Redmi Android13 прошли все три проверки; приложение после проверки Redmi повторно запущено (`Status: ok`). Android `:app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug --no-daemon` — BUILD SUCCESSFUL; 198/198 unit tests, 0 failures/errors/skips. Это доказывает восстановление SQLite после force-stop mid-transaction на этих двух средах; не доказывает power-loss/hard hardware crash/disk-full, restore/uninstall/key rotation или WAL поддержку. WAL остаётся выключенным.

P1 остаётся открыт по перечисленным gates. P3–P6 integration и P7–P9 остаются незакрыты. Код/журнал из ACT-0067 ещё не синхронизированы в Git на момент записи; до передачи повторить `git diff --check`, secret scan и проверить точный remote hash.

### Идея, которую нельзя потерять

Memora — независимый многоязычный персональный AI-секретарь с управляемой пользователем долговременной памятью. Пользователь говорит или пишет естественно; система связывает сведения с людьми, проектами, деньгами, долгами, задачами и календарём; возвращает контекст с источниками и помогает вовремя действовать.

Обещание: «Расскажи — я запомню. Спроси — я найду. Забудь — я напомню». Оно ограничено сохранёнными данными, правами и проверяемым состоянием. LLM не является источником финансовой истины. Нужны происхождение, история исправлений, точные деньги, время, защита от повторов и возможность сказать «не знаю».

## Как продолжать дневник

После каждого содержательного этапа обновлять актуальное состояние и добавлять запись с полями:

Параллельно дополнять [ACTION_LOG.md](ACTION_LOG.md): конкретные действия, проверки, результат, Git и следующий шаг. Этот порядок обязателен также для исправлений, сборок, установок и передачи работы через Git.

1. Дата в часовом поясе пользователя; задача и цель.
2. Прямые решения пользователя отдельно от инженерных рекомендаций.
3. Фактически изменённые файлы и достигнутый результат.
4. Проверки: что запускалось, что прошло, что не проверялось и почему.
5. Открытые вопросы, риски и незавершённая работа.
6. Следующий конкретный шаг; ветка/коммит при наличии и состояние локальных изменений.

Не стирать исторические решения молча: отмечать, чем и когда они заменены. Не копировать всю переписку; сохранять факты и ссылки. Если дневник расходится с кодом, сначала выяснить причину и скорректировать запись. Никогда не отмечать задачу выполненной только потому, что она была запланирована.

# P0: первые машинные контракты агента v1

Агрегатор [evaluation_metrics.py](evaluation_metrics.py) считает holdout coverage, language/route outcome rates, критические ошибки и median/p95 latency по обезличенным меткам и исходам. Он требует раздельные paraphrase groups, возвращает `null` для отсутствующего среза и сравнивает заполненный отчёт с порогами из `evaluation-plan.json`. Это только инфраструктура оценки: holdout corpus, live Gemini, real human speech и device acceptance не запускались; метрика никогда не заменяет недельное решение владельца.

В этой версии есть строгие model proposal forms для всех 32 плановых инструментов, app command envelopes для 23 изменяющих инструментов, типизированные result variants, синтетические примеры и [eval manifest](eval-manifest.json). Это контрактный каталог MEM-12.10, не runtime, не Firebase wire API и не разрешение модели выполнять действия. Все 32 policy entry остаются `runtimeEnabled=false`. Существующие функции приложения не переключены на эти контракты. Evaluation manifest описывает только детерминированную синтетическую проверку контрактов; holdout качества модели не запускался.

`query_finance` только read-only: сумму вычисляет доверенный локальный handler по точным целым minor units одной валюты и подтверждающим event IDs. Табличные ответы включают schemaVersion/column IDs; typed aggregate вычисляет приложение. Уточнение и `prepare_changes` не коммитят данные. Мутационные схемы требуют app-authored IDs и точных expected versions; settlement/correction/schema change/deletion имеют confirmation bindings. Синтетические binders покрывают критичные cross-field checks, но не заменяют исполнение/транзакционные проверки всех инструментов.

- `model-tool-call.schema.json`: строгая форма аргументов; модель не может назначать scope, actor, command ID и approval. Нет произвольного SQL/файлов.
- `command-envelope.schema.json`: доверенные поля добавляет приложение: IDs, source/evidence, versions и permission snapshot. JSON Schema проверяет форму, а не подлинность полей.
- `tool-result.schema.json`: типы успеха, пустого/частичного результата, подготовленного плана, конфликта и отказа. `prepared` не означает commit; result binders связывают критичные IDs/версии/evidence с запросом.
- `fixtures/all-proposals.json` даёт синтетическую валидную форму каждого из 32 предложений; остальные fixtures — межъязыковые golden-векторы, доменные состояния и негативные примеры.
- `policy-matrix.json` — проектная матрица для 32 инструментов из руководства с deny-by-default. Во всех строках `runtimeEnabled` равно false; запись в матрице сама по себе не выдаёт разрешения и не включает инструмент. Общие условия, в том числе обязательная проверка области и версий, необходимость Undo для автоматических изменений и preview массового действия, применяются поверх классификации каждой строки.
- `confirmation-proof.schema.json` и Kotlin `ConfirmationGate` — проектный формат и чистая предварительная проверка времени, статуса, области, автора, digest, версий целей и разрешений. Это не выпуск пользовательского подтверждения и не потребление токена. Перед commit будущий runtime обязан взять запись из доверенного хранилища, повторить проверку текущих полномочий и атомарно отметить подтверждение использованным вместе с эффектом; параллельные команды не должны обе пройти. При неоднозначности/коррекции часов требуется отдельная fail-closed политика: простое сравнение системных часов не доказывает, что 10 минут реального времени не истекли.
- `consent-record.schema.json`, `consent-ticket.schema.json` и чистый Kotlin `AgentConsentGate` описывают отдельные будущие согласия на текущий запрос и на передачу фрагмента сохранённой памяти. Тестовый preflight связывает scope, провайдера, категории, версию политики, ревизии, поколение сессии и digest полезной нагрузки; отзыв, новая ревизия или другая нагрузка блокируют старый ticket. Ticket — не секрет и не самостоятельное разрешение: выдача UI, доверенное хранилище, актуальные права и синхронизация отзыва с началом отправки пока не реализованы. Уже переданные данные отозвать невозможно.
- Чистые Kotlin `CommandLifecycle` и `CommandReplay` задают допустимые переходы, отличие отмены до commit от неопределённого результата и проверку совпадения scope/ID/digest. Вызовы `ConfirmationGranted`, `CommitConfirmed` и `Reconcile` являются событиями доверенного будущего runtime, а не предложениями модели; эти классы не подтверждают право, не сохраняют журнал и не могут сами установить факт commit. Доказательство транзакции и повторная проверка доступа к результату требуют P1/P2.

Для `read_records` результат сверяется с запрошенными ID/типами и допустимыми полями; частичная выдача не объявляется полной. `resolve_person` возвращает список кандидатов: одинаковые имена не склеиваются и не доказывают выбор одного человека. Пока это только формы и синтетический тест, не действующий поиск и не проверка разрешений на личные записи.

`update_note` в текущем срезе принимает только непустой patch заголовка и/или тела. Отсутствующее поле сохраняется; `null`, пустой patch и неизвестные поля отклоняются. Связи не меняются этим вариантом: соответствующий контракт будет подготовлен отдельно. Приложение выделяет `newRevisionId`, а не принимает его от модели; команда связывается с точной ожидаемой версией заметки. Result для note содержит noteId и revisionId; тестовый связующий валидатор сверяет их с командой и её evidence, но это ещё не подтверждение фактической записи.

`create_person` и `create_project` не принимают от модели ID новой сущности; его выделяет приложение. Создание проекта предполагает начальный статус ACTIVE в доверенной команде; модель не вправе передать другой статус при создании. Для `update_person`/`update_project` требуется точная ожидаемая версия. Поддерживаются только перечисленные поля patch; создание одноимённого человека не означает автоматическое слияние. В тестовом контракте созданная сущность получает версию 1, изменение — предыдущую версию плюс 1, а no-change не увеличивает версию. Это правила будущих обработчиков, не доказательство их реализации.

Для `link_records` необходимо явно задать тип и оба разных объекта; ID новой связи выделяет приложение, команда привязана к версиям обоих объектов. Для `unlink_records` требуется версия конкретной связи; удаление связи не удаляет связанные объекты. Самостоятельное связывание допустимо только при выполнении всех общих условий матрицы; разрешённость сочетания типов и смысл отношения остаются проверкой будущего доменного слоя. Совпадающие объекты, неизвестные поля и подмена ID со стороны модели отклоняются. Этот срез не выполняет связей и не разрешает использовать их до реализации и проверки обработчиков.

Срез `preview_delete` / `commit_delete` описывает только **перемещение в корзину**, не окончательное стирание. Предпросмотр фиксирует область, исходную версию запроса, каждый целевой объект и зависимую связь с их версиями; суммарно не более 100 элементов, превышение не обрезается молча. `planDigest` — SHA-256 канонических байтов полного объекта предпросмотра без самого `planDigest`; порядок массивов сохраняется. До применения будущий runtime проверяет, что предпросмотр относится к запросу, что область/источник/версии и действие не изменились, а подтверждение выдано пользователем и актуально. Модель может предложить ID предпросмотра, но не назначает `confirmationId`. Результат содержит все изменённые объекты и связи с новыми версиями; отсутствие одной части не допускается как успешный атомарный commit. Схема, Python-сверка и наличие ID подтверждения не доказывают, что подтверждение действительно выдано, что все последствия найдены или что транзакция выполнена.

В `create_task` и `update_task` дата без часа сохраняется с точностью date; напоминание требует явно заданных локальных даты/времени и IANA timezone. При изменении срока на дату без часа или его удалении требуется явное отключение напоминания: нельзя молча менять другое поле. Несуществующее и повторяющееся локальное время отклоняется для уточнения. Тесты используют закреплённый `tzdata` и проверяют DST; будущий runtime должен независимо проверить используемую версию базы зон и не переинтерпретировать подтверждённую дату незаметно. Result отделяет запись задачи от статуса планирования/отмены напоминания; SCHEDULED не доказывает доставку. Часть условий зависит от текущей версии задачи и должна повторно проверяться в транзакции.

Для этого узкого v1-среза `payloadDigest` — SHA-256 от канонических UTF-8 байтов envelope без полей `payloadDigest` и `confirmationId`. Подтверждение выдаётся позднее и отдельно связывается с этим digest; исключение ID подтверждения не освобождает от проверки самого подтверждения и его области/срока. Все остальные поля, включая ID команды/хода, цель, текст, ссылки, версии и permission snapshot, входят в digest. Изменение любого из них требует нового digest и повторной проверки соответствующего подтверждения.

Канонический формат: JSON без пробелов, ключи объектов только ASCII и отсортированы по возрастанию байтов; порядок массивов сохраняется; целые числа в десятичном виде, диапазон signed 64-bit, без дробных значений; литералы `true`, `false`, `null` в нижнем регистре. Строки кодируются UTF-8 без Unicode-нормализации, символы `"`, `\\` и управляющие символы экранируются по правилам Python `json.dumps(ensure_ascii=False)`: короткие escape `\b`, `\t`, `\n`, `\f`, `\r`, остальные U+0000–U+001F как строчные `\u00xx`; slash и прочие корректные символы не экранируются. Непарные суррогаты, повторные ключи и числа с десятичной точкой или экспонентой отклоняются до вычисления. Неизвестные поля сначала отклоняет схема. Подтверждение никогда не доверяется только потому, что его ID присутствует в envelope.

JSON Schema ограничивает число Unicode code points, а продуктовый контракт — UTF-16 units: дополнительная семантическая проверка обязательна. Проверяются непарные суррогаты и текст из пробелов. Для связанных объектов expectedVersions должны покрывать все ссылки без повторяющихся ID. Для периода начало строго раньше исключающего конца. Парсер в тестах отвергает повторные ключи, дробные числа и NaN; Android-реализация обязана отдельно обеспечить такие же свойства без предположения о поведении `JSONObject`.

В тестах используются только локальные файлы; сеть, Firebase и реальные данные не нужны. Установка проверочной зависимости — отдельный dev-окружение, не APK:

```sh
python3 -m venv .venv-agent-contracts
. .venv-agent-contracts/bin/activate
pip install -r tests/agent_contracts/requirements.txt
python -m unittest discover -s tests/agent_contracts -v
```

Схема сама не проверяет права, scope, существование источников и объектов, привязку подтверждений, валидность digest, соответствие исходной просьбе, полноту чтения, транзакции и фактическое сохранение. Тестовый Python-эталон сверяет digest; отдельный Kotlin-код также проходит golden-векторы команды и предпросмотра удаления и негативные проверки, но не подключён к пользовательским командам. Совпадение digest не доказывает полноту предпросмотра или право на удаление. Будущая серверная реализация должна независимо пройти те же векторы. Для совместимости изменения несовместимых схем требуют новой версии и проверок старых pending calls. Нельзя подключать эти прототипы к пользовательским данным до реализации этих границ.
